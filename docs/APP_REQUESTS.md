# Application requests: duplicate check, moderator review, approval

This feature is implemented without a GitHub OAuth token inside the
desktop application. Anonymous GitHub REST API calls are read-only.
Posting an issue takes place in the user's own browser and requires the
user to sign into GitHub and confirm.

## User experience

1. In **Discover**, click **Richiedi un'app**.
2. Enter application name, publisher, official HTTPS site, optional
   public GitHub repository, supported platforms, free-license type and
   a short description.
3. Click **Verifica duplicati**. The desktop backend searches the bundled
   and signed catalogs (UI), the live maintainer-approved community feed,
   and up to 500 open/closed GitHub issues.
4. If an existing app or a request is found, the matching entries
   appear with clickable links, and duplicate submission is blocked.
5. On no matches, click **Apri richiesta su GitHub**. A prefilled issue
   opens in the user's browser. **The user must submit it on GitHub**.
6. An issue is not automatically an approved application.

A saturated/incomplete issue check blocks the create action rather than
claiming to have found no duplicates. GitHub API rate limits and
connectivity failures are surfaced to the user.

## Maintainer review

For a request generated by the launcher:

1. Open the GitHub issue with title `[App Request] ...` and examine
   the official URL, publisher, license, supported OSes, safety and
   distribution. The machine-readable HTML comment in the body contains
   structured request metadata.
2. A maintainer with `write`, `maintain` or `admin` permissions comments
   **`/approve-app`** on that open issue.
3. GitHub Actions runs `.github/workflows/approve-app-request.yml`.
   It independently checks the commenter's effective repository permission
   and validates the original issue's structured fields.
4. The workflow creates branch `app-requests/issue-<number>` and opens a
   review PR proposing a metadata-only entry in
   `catalog/approved-community.json`. It does **not** merge.
5. The maintainer reviews the PR and runs CI, which validates both
   the existing bundled catalog and the approved community feed.
6. **Only merging this PR into main** publishes the new approved entry.
   GitHub closes the linked issue when the PR merges.
7. The launcher reads only `main`'s HTTPS approved-community feed on startup
   and when **Aggiorna approvate** is clicked. No application restart is
   required after a successful refresh.

### GitHub repository setting required

GitHub's default Actions setting can disallow bot-created PRs.
In repository **Settings → Actions → General → Workflow permissions**,
enable **Allow GitHub Actions to create and approve pull requests**.
Without that setting the workflow can fail to create the review PR.
The maintainer must then create a PR editing
`catalog/approved-community.json` manually. The requirement to
review and merge remains the same.

The workflow intentionally uses **no stored personal access token** in
the launcher. A maintainer's GitHub account is never requested by it.

## Security separation

- An Issue is an *unreviewed user suggestion*. It is never read as a native
  installer manifest.
- The reviewed feed is served from the repository's `main` branch
  over HTTPS. No fork/feature branch can inject approved catalog entries.
- App names, URLs, platforms, descriptions and pricing are checked for
  basic format; the maintainer remains responsible for verifying their
  factual accuracy, authorship and licensing.
- Approved entries have only display and link metadata (not custom
  binaries, installers, scripts, package manager commands or icons).
- Native `installable_app_ids` and the Rust installer allowlists remain
  unchanged. A catalog approval alone **does not enable native installation**
  or verified updates for that app.
- Repeated `/approve-app` requests are idempotent in intent: the workflow
  refuses to reuse an existing issue review branch or duplicate an approved
  ID. Two concurrent approvals may require a maintainer to resolve
  a catalog merge conflict.

## Limitations

- GitHub's public API has unauthenticated rate limits. A check fails
  closed if it cannot complete. At most 500 recent issues are scanned;
  if the result may be truncated, direct request submission is disabled.
- Duplicate checks are exact by repository or official site, or
  case-insensitive by name. Similar spellings may require manual review.
- GitHub issues can be created from the GitHub website without using the
  structured launcher flow, but automatic PR preparation requires the
  machine-readable issue body generated by Creative Hub.
- No background approval notifications, OAuth login or application
  database are included in this phase.
